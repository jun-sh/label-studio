# ego-001 使用手册

**130 采集 · 34 平台 · 一次录制 = 一个 episode**

| 设备 | IP | 角色 |
|------|-----|------|
| 采集站 130 | `10.10.10.130` / 手机热点 `192.168.8.1` | 录制 + 上传 |
| 平台 34 | `10.10.10.34:8080` | 派生 + 后处理 + 浏览 |

---

## 一、日常流程（最常用）

```text
1. 130 手机 UI：开始录制 → 结束录制
2. 130 终端：  ego-upload ego-001
3. 等 ~2 分钟（34 derive → Collection 可预览）
4. 浏览器打开 Collection 验收；egodome 异步批处理（见下）
```

### 时效承诺（产品分层）

| 阶段 | 操作员可感知页面 | 目标时效 | 说明 |
|------|------------------|----------|------|
| **采集质检** | `/collection?station=ego-001` | 上传后 **~2 分钟内** 可见 derive 结果 | P1 derive：`DERIVE_EXTRACT_CONCURRENCY=4` |
| **训练交付** | `/data/egodome` | **异步 30–60 分钟**（班次批量） | WiLoR convert 后台跑，不阻塞录下一班 |

单段上传后只需等 Collection；**不必等 egodome** 再录下一段。`ego-process` / watcher 会在后台批处理 convert。

### 130 上传

```bash
ego-upload ego-001
```

默认会上传 **所有 session** 里状态为 CLOSED 的待传段（一次班次录多次也只需执行一次），并通知 34 自动跑后处理。

只上传某一个 session（高级）：

```bash
ego-upload ego-001 --session-id sess_xxxxxxxx
```

仅上传、不触发 egodome 后处理：

```bash
ego-upload ego-001 --no-notify
```

### 浏览器验收

| 页面 | 地址 | 看什么 |
|------|------|--------|
| 采集质检 | http://10.10.10.34:8080/collection?station=ego-001 | 实时派生结果，按 session 列表 |
| 数据集 | http://10.10.10.34:8080/data/egodome | 后处理完成的数据集，按 episode 列表 |

**正常：** Collection 在上传后数分钟内逐条增加；egodome episode 在 `ego-process` 批处理完成后与 Collection 数量一致。

### 34 兜底（自动失败时）

```bash
ego-process ego-001
```

或从 34 一键（含 SSH 上传）：

```bash
ego-deliver ego-001
```

## 二、数据流（理解两个页面为何不同步）

```text
130 录制
  → segments/（本地段）
  → ego-upload
  → 34 ingest + derive-worker     → /collection 可见
  → ego-process（convert + sync） → /data/egodome 可见
```

- **Collection**：derive 完成即有（快）
- **egodome**：必须跑完 convert + Viewer 同步（慢一步）

`ego-upload` 默认会 notify 34；watcher 约 30s 内触发 `ego-process`。

## 六、排障

| 现象 | 处理 |
|------|------|
| Collection 有、egodome 少 | 34 执行 `ego-process ego-001`；查 watcher timer |
| 130 段数很多、Collection 很少 | 确认是否跑过 `ego-upload`；新版会扫**全部 session** |
| 上传后无 notify | 查 `~/.config/ego-station.env` 中 `EGO_NOTIFY_PROCESS=1` |
| derive 卡 UPLOADED | `docker logs data-lab-derive-worker-1 --since 1h` |
| 采集启动失败 | `ego-130-verify-production.sh`；查 OAK 连接 |

## 九、MCAP Pilot（ego-mcap-pilot · Track 1）

与生产 `ego-001`（tar.zst · `:7862`）**隔离**的试点站，ingest 走 **`:7863`** pilot overlay。

### 130 真机 MCAP 短录 SOP（P1a · VPU H.264）

`preview-standby` 会独占 OAK，**录制前必须停 preview**，录完再恢复。

```bash
# 130 录制前置
systemctl --user stop ecs-preview-standby
systemctl --user stop ecs-record-oak-mcap
rm -f ~/cache/ego-001/checkpoint.json ~/cache/ego-001/strict_emit_ts.json \
      ~/cache/ego-001/segments/checkpoint.json ~/cache/ego-001/segments/strict_emit_ts.json
systemctl --user start ecs-record-oak-mcap
# 等待 episode 结束（或 systemctl --user stop ecs-record-oak-mcap）
ego-upload ego-001 --notify
# 恢复预览
systemctl --user start ecs-preview-standby
```

| 项 | 说明 |
|----|------|
| 采集 unit | `ecs-record-oak-mcap.service`（勿用手动 CLI 与 preview 并发） |
| 段边界 | P1a：段关闭前 encoder flush + IDR；MCAP 四路帧数必须一致 |
| 34 验收 | derive 须 G1/G3/G2b/**G7=1.0** 才算可播 |

**H.264 trim-to-IDR（P1a.1 · derive 兜底）**：原始 MCAP 完整保留；`mcap-materialize.py` 在 derive 阶段对每路码流丢弃首个 IDR 之前的包，再 remux。长期目标仍是 130 源端首包 IDR（P1a.1 源端方案）。

#### 130 真机测试常见坑（2026-08-30 签收）

| 坑点 | 说明 |
|------|------|
| 上传 URL | **必须** `:7863` pilot overlay；误用 `:8080` 会把 `.mcap.zst` 当 `tar.zst` 解析 → `invalid header` |
| 录制时长 | `record_oak_stream.py --episode-seconds` **不生效**；受 `EGO_STRICT_EPISODE_SECONDS` 控制（默认 86400）。短测需 `export EGO_STRICT_EPISODE_SECONDS=35` 并清理 `checkpoint.json` / `strict_emit_ts.json` |
| 站 ID 覆盖 | pilot systemd **不再**加载 `ego-station.env`；`ego-upload ego-mcap-pilot` 内置 `:7863` 路径 |
| OAK 占用 | 录制前停 `ecs-preview-standby`（`ego-130-record-mcap-pilot.sh` 自动处理） |
| checkpoint | 每次短测须清 `~/cache/ego-mcap-pilot/checkpoint.json`，否则 `frame_index` 续号 → derive `empty_chunk` |
| 相机 topic | 采集侧键为 `observation.images.camera_*`；`mcap_segment_writer` 须 `normalize_camera_jpegs()` 映射为 `front_left` 等短键 |
| 双归档 | 勿同时上传 `tar.zst` 与 `mcap.zst`；残留 `tar.zst` 会导致 derive `PARQUET_INDEX_GAP` |

真机参考 session：`sess_104229409ad24b9e97fad0150ad32b09`（950 帧 · 4×1280×800 HW-JPEG · dropped=0）。
